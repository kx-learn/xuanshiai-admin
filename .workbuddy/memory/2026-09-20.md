- 排查手法：先 `Get-NetTCPConnection -LocalPort 8000 -State Listen` 拿到 PID，对照该进程的启动时间是否早于本次改动；**不要只看源码就断定已生效**。
- 处理：`taskkill /PID <pid> /F` 后重新 `./.venv/Scripts/python.exe main.py`（后台）。启动要跑数据库自动初始化（225 张表），约 20~30 秒才 ready，用轮询 `/openapi.json` 判断就绪，别用固定 sleep。
- 结论：**改完后端接口后，务必重启并用 openapi.json 复核**，否则会误判成前端问题。

### 业务口径（源码 `app/services/meeting.py` 确认，非文档推测）

- **申请状态机**：`SUBMITTED → CONTACTED → ACCEPTED`；`SUBMITTED/CONTACTED/ACCEPTED → DECLINED/CLOSED`。
- **只有 `ACCEPTED` 能排期**，否则 409「只有双方接受的约见申请才能安排约会」；排期=POST schedule，非 PATCH status。
- **`DECLINED`/`CLOSED` 必须带 `reason`**，否则 **422**；且会 `matchmaker_service_quota.available_count += 1`（退次数）+ 发通知 + 审计日志。
- **`SUBMITTED` 不由后台设置**（用户初始态），Admin 只能写 CONTACTED/ACCEPTED/DECLINED/CLOSED。
- 状态标记口径：`DONE = {ACCEPTED, DECLINED, CLOSED}` → 「已处理」，其余「待处理」。与 `status_group=pending|done` 对齐。
- **`met` 参数映射**：`met=wait` → `SCHEDULED/REMINDED`；`met=met` → `CHECKED_IN/COMPLETED`。注意 `met=wait` **不含** `CANCELLED/NO_SHOW`。
- **约会状态**：SCHEDULED 待见面 / REMINDED 已提醒 / CHECKED_IN 已见面 / COMPLETED 已完成 / CANCELLED 已取消 / NO_SHOW 未见面。`CHECKED_IN|COMPLETED` 计入「成功见面」。
- ⚠️ 后端 `/options` 给的 `record_status` 文案是「已签到 / 未到场」，与前端页面既有文案「已见面 / 未见面」不一致。**前端保留自己的文案**（与会员端「我的约会」口径一致），后端 options 的 label 只作参考。
- `dating-records` 同时返回本人作为 from 或 to 的行 → 前端「见谁」列需按 `from_user_id === memberId` 判断对方是谁。
