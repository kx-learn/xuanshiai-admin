# 后端接口缺失清单（需后端新增）

> **核对基准**：线上真实 `openapi.json` 快照 — `.workbuddy/refsite/live_openapi.json`
> 共 **663 条路由**，其中 `/api/v1/admin/*` **296 条**
> 生成时间：2026-10-13
> 说明：本清单已用线上 openapi **逐条复核**，列出来的都是线上确实不存在的接口，不含"源码里有但没部署"的情况。

---

## 零、结论速览

| 类别 | 数量 | 说明 |
|---|---|---|
| **A 类：后端完全没有，必须新增接口** | **11 组** | 页面已存在但无数据可存可取，见第一节 |
| **B 类：接口有，但字段缺** | **3 处** | 需后端加字段，见第二节 |
| **C 类：接口齐全、纯前端未接** | **42 个页面** | **不是后端问题**，见第三节（其中大部分可走通用配置接口） |

**最重要的发现**：后端已有通用配置接口 `GET|PATCH /admin/configs/{namespace}`（自由 `config` 字典 + `version` + `change_summary`，另带审计日志）。
因此第三节里 **20 多个"纯静态配置页"不需要后端新增接口**，前端接到这个通用接口即可。真正需要后端动手的只有 A 类 11 组 + B 类 3 处。

## 一、A 类：后端完全没有，必须新增（按优先级）

### A1 短信管理 ⭐最高优先 — 4 个页面 + 3 处被依赖

**受影响页面**：`sms-signature`（签名）、`sms-notices`（通知模板）、`sms-group`（群发）、`sms-record`（记录）
**额外依赖位置**：会员资料页「短信模板 / 确定发送」、活动列表页「群发短信」、线下VIP 见面提醒「短信提醒」

**线上现状**：只有 `/api/v1/auth/sms/send`（登录验证码）和 `/api/v1/commonadmin/api/sms/getStastics`（余量统计，非 admin 域）。
**签名 / 模板 / 群发 / 发送记录 四类能力全无。**

**建议新增**：
```
GET    /admin/sms/signatures              签名列表（报备状态）
POST   /admin/sms/signatures              新增签名
PATCH  /admin/sms/signatures/{id}
DELETE /admin/sms/signatures/{id}
GET    /admin/sms/templates               通知模板列表
POST   /admin/sms/templates
PATCH  /admin/sms/templates/{id}
DELETE /admin/sms/templates/{id}
POST   /admin/sms/send                    群发（user_ids + template_id + 变量）
GET    /admin/sms/records                 发送记录（分页 + 时间/模板/状态筛选）
GET    /admin/sms/quota                   短信余量
```

### A9 会员侧弃海 ⭐（当前页面已就位、只剩空表）

**受影响页面**：`love-user-list` 的「弃海会员(N)」「弃海记录」两个子 Tab

**线上现状**：弃海能力**只在客源侧**存在——
```
✅ /admin/customer-leads/abandoned            弃海客源列表
✅ /admin/customer-leads/abandonments         弃海记录
✅ /admin/customer-leads/{lead_id}/abandon    放入弃海
❌ 会员侧：无 /admin/members/abandoned、无 abandonments、无 /members/{id}/abandon
```
会员列表接口 `vip_filter` 只支持 `all / offline_vip / online_vip / store_verified / **exclude_abandoned**`——
**只能"排除弃海会员"，无法"只要弃海会员"**，所以列表和计数都取不到（目前 Tab 计数被迫取客源弃海数，数字不对）。

**建议新增**：
```
GET    /admin/members/abandoned               弃海会员列表（分页 + 筛选，复用会员列表返回结构）
POST   /admin/members/{member_id}/abandon     放入弃海（reason + 放弃类型）
POST   /admin/members/{member_id}/restore     捞取（分派到指定红娘）
GET    /admin/members/abandonments            弃海记录（分页 + 放弃人 / 类型 / 时间 / 分派状态）
```
> 补充口径：后端 schema 里 `abandoned` 的定义是「来源客源 `status=LOST`」，
> 所以新增的 `/admin/members/abandoned` 内部按「会员关联客源 status=LOST」过滤即可，不用建新表。
